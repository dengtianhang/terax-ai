# Terax 请求分类与澄清

## 目标

把用户请求分成 **Bug**、**需求** 或 **待确认**，并让记录、讨论、实现、验证形成闭环。默认使用简体中文；代码标识符、命令、API 和错误信息保留原文。

## 第一原则

- 不把新能力误判成 Bug，也不把现有行为异常包装成需求。
- 不因用户说“改一下”就直接写代码；先判断目标是否明确。
- 需求目标、范围或验收标准说不清时，暂停实现，继续澄清或登记为待处理。
- 用户明确要求立即修复且根因明确时，可直接进入 Bug 修复流程，但仍要登记和验证。
- 只修改当前 Terax 项目；不修改项目外文件。

## 分类规则

### Bug
现有能力本应如此但实际不对，包括：错误、回归、崩溃、偏移、无法关闭、重复实例、数据丢失、性能退化、文案遗漏、平台差异异常。

关键词仅作线索，不作唯一依据：`不对`、`没变化`、`报错`、`无法`、`还是`、`突然`、`回归`、`崩溃`。

记录到 `docs/BUGS.md`，编号使用 `BUG-NNN`。至少记录：状态、优先级、复现条件、实际现象、期望行为、影响范围、原因、修复、验证。

### 需求
当前不存在的能力，或用户明确提出的产品改进、体验优化、策略调整、默认行为变化。

关键词仅作线索，不作唯一依据：`增加`、`支持`、`希望`、`能否`、`最好`、`优化`、`提供`。

记录到 `docs/REQUIREMENTS.md`，编号使用 `REQ-NNN`。先写清单项 `[ ]`，再补详情：状态、优先级、背景、目标、范围、非目标、验收标准。

### 待确认
一句话同时包含需求和 Bug、用户期望不明确、现有行为尚未确认、或实现方向会显著改变用户体验时，先不改代码。指出判断依据，并提出最少量关键问题。

## 需求澄清流程

按优先级逐层询问，不一次抛出大问卷。每轮最多 3 个问题，优先问会改变方案的问题：

1. **问题与用户**：解决谁的什么痛点？当前替代方案是什么？
2. **目标与结果**：完成后用户具体看到什么变化？
3. **范围**：适用页面、平台、项目、数据和生命周期是什么？
4. **交互**：入口、默认值、状态、空状态、错误状态、取消和恢复如何表现？
5. **边界**：重复、无效、权限、并发、多屏、重启、升级、历史数据如何处理？
6. **验收**：用 2–5 条可观察标准判断完成；同时确认优先级和非目标。

已有上下文能回答的问题不重复询问。用户回答后，先用短句复述“目标、范围、验收、暂不做”，让用户纠正；确认清楚后才实现。

## 执行门槛

需求只有在以下内容明确后才能实现：

- 目标和用户价值
- 范围与非目标
- 核心交互和默认行为
- 关键边界条件
- 验收标准
- 优先级或实现顺序

Bug 只有在以下内容足够明确后才能修复：

- 实际行为与期望行为
- 可复现路径或已获得的日志/截图/代码证据
- 影响范围和平台条件
- 可验证的修复结果

若仍有关键歧义：更新对应文档为“待澄清”，不写实现代码。

## 文档与提交

- 先查现有编号、清单和详情，避免重复记录。
- 先更新 `docs/REQUIREMENTS.md` 或 `docs/BUGS.md`，再改代码。
- `[ ]` 表示待处理、待澄清或暂不修复；`[x]` 只表示已验证完成。
- 完成后更新状态、验收结果和关联提交。
- 提交信息带编号，例如 `feat REQ-008 ...`、`fix BUG-002 ...`。
- 新增能力与异常同时出现时拆成独立 `REQ` 和 `BUG`，分别记录、分别验收。

## 回复格式

### 分类明确时

```text
分类：需求 | Bug
编号：REQ-NNN | BUG-NNN
判断：一句话说明依据
当前记录：已登记到对应文档
下一步：澄清问题 | 定位复现 | 实施 | 验证
```

### 需求未澄清时

```text
分类：需求（待澄清）
目标理解：...
需要确认：
1. ...
2. ...
暂不改代码；确认后登记/实施。
```

### Bug 证据不足时

```text
分类：Bug（待复现）
已知现象：...
缺少证据：...
下一步：先收集日志/复现路径，不直接猜测修复。
```

## Terax 示例

- “设置弹框二屏偏右上” → `BUG`：现有定位行为错误。
- “增加最近访问目录，快速切换项目” → `REQ`：新增能力，需先明确列表入口、数量、持久化和失效目录处理。
- “一个空间能否包含多个项目” → 先确认当前产品模型；若提出支持多根项目则是 `REQ`，不是 Bug。
